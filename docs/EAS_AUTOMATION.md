# Автоматизация доставки изменений: OTA (EAS Update) / NATIVE_BUILD (EAS Build)

Статус проекта: **BARE workflow** (нативный `android/` закоммичен, `expo prebuild` уже выполнен).
Пакет `space.ghostcloud.app`, проект EAS `@ghost552/ghostcloud`.

---

## 1. Базовые принципы

Обновление по воздуху (OTA) возможно **только** тогда, когда изменение полностью
укладывается в JS-бандл и совместимо с уже установленным нативным рантаймом.
Если изменение трогает нативный код, ресурсы, манифест, права, рантайм-версию или
нативные зависимости — нужна новая сборка (или ручная проверка).

Вердикты классификатора (`scripts/ota/classify.mjs`):

| Вердикт | Код выхода | Значение |
|---|---|---|
| `OTA` | 0 | можно публиковать через `eas update` |
| `NATIVE_BUILD` | 10 | нужна новая сборка `eas build` |
| `REVIEW_REQUIRED` | 20 | определить безопасно нельзя — решает человек |

## 2. Текущая конфигурация

- **`runtimeVersion`**: зафиксирован `1.0.0` (в `app.json` и в текущих бинарниках пользователей).
  Любое изменение рантайма = новая сборка. Политика `appVersion` снята намеренно:
  она ломала доставку (в бинарниках было `1.0.0`, а публикации шли с версией из `app.json`).
- **Каналы**: `development`, `preview`, `production` (объявлены в `eas.json`).
  Канал зашивается в бинарник при сборке:
  - локальные/ручные сборки получают канал из `app.json → updates.requestHeaders["expo-channel-name"]` (сейчас `production`);
  - `eas build --profile <p>` берёт канал из `channel` соответствующего профиля.
- **Проверка обновлений**: при каждом запуске (`CHECK_ON_LAUNCH=ALWAYS`), применяется при следующем запуске. Поддерживаются BSDIFF-патчи (маленькие диффы).

## 3. Классификатор (`npm run ota:analyze`)

Анализирует git-дифф (по умолчанию `HEAD~1..HEAD`, можно `--range A..B` или `--commit <sha>`).

Порядок приоритетов (жёсткий):

1. **Правила нативной безопасности** (детерминированные, вето):
   - пути `android/**`, нативная часть `modules/*/android/**` (всё кроме `.ts/.tsx/.js/.jsx`);
   - расширения `.so`, `.aar`, `.jar`, `.keystore`;
   - папки `core-src/**`.
2. **Совместимость рантайма**: изменения в `app.json` — `runtimeVersion`, `version`, `android` (permissions и т.п.), `plugins`, `updates` (url/каналы) → `NATIVE_BUILD`.
3. **Анализ зависимостей**: дельта `package.json` сверяется с `deps-registry.json`;
   добавление/удаление/смена версии нативного пакета → `NATIVE_BUILD`;
   неизвестный пакет → `REVIEW_REQUIRED`. Дополнительно сканируются новые вызовы
   `XrayNative.*`/`XrayCore.*` по снимку `native-api.json` — вызов несуществующего
   метода в установленных бинарниках → `REVIEW_REQUIRED`.
4. **Статический анализ** (`--static`): `tsc --noEmit` должен пройти.
5. **ИИ-анализ** (`--ai-verdict`): может **только ужесточить** вердикт
   (например `OTA → REVIEW_REQUIRED`), но **никогда** понизить: запрос `--ai-verdict OTA`
   против нативного диффа будет отклонён. Это проверяется тестами.

**Белый список для OTA** (без нативных правил): `src/**/*.{ts,tsx,js,jsx}`, `App.tsx`,
`index.ts`, новые картинки `assets/**` подключаемые через `require()`, `docs/**`,
`README.md`, `scripts/**`, `babel.config.js`, `tsconfig.json`.

**Требуют ручной проверки**: `eas.json`, `metro.config.js`, `modules/*/package.json`,
`package-lock.json` без `package.json`, любые неизвестные файлы.

Тесты: `npm run ota:test` (17 сценариев на реальных временных git-репозиториях).

## 4. Публикация

### Черновик / тест — ветка `preview`

```bash
npm run ota:analyze            # посмотреть вердикт
npm run ota:preview -- -m "описание изменения"
```

Публикация разрешена только при вердикте `OTA` (для `preview` можно форсировать
`--force`, для `production` — никогда). Перед публикацией проверяются: авторизация,
чистое рабочее дерево, классификатор.

### Продакшен — двойной гейт

```bash
# оба условия обязательны одновременно:
GC_PUBLISH_PROD=yes npm run ota:production -- --confirm-production -m "описание"
```

Скрипт откажет, если отсутствует флаг **или** переменная окружения, **или**
вердикт не `OTA`. Это защищает от случайной продакшен-публикации агентом/скриптом.

После публикации запись сохраняется в `scripts/ota/history.json`.

### Каналы и ветки

| Канал | Для чего | Как получает обновления |
|---|---|---|
| `development` | отладочные сборки | ветка `development` |
| `preview` | тестовые сборки, проверка обновлений | ветка `preview` |
| `production` | пользователи | ветка `production` (публикация только через двойной гейт) |

Синхронизация ветки с каналом: `npx eas channel:edit production --branch production`.

## 5. Rollback (откат)

1. **Посмотреть историю**: `npm run ota:status` (локальный `history.json` + серверные `channel:list`/`update:list`).
2. **Откат на предыдущую группу**:
   ```bash
   npm run ota:rollback                          # для preview
   GC_PUBLISH_PROD=yes node scripts/ota/rollback.mjs --branch production --previous --confirm-production -m "откат: причина"
   ```
   Работает через `eas update:republish` — сервер атомарно указывает ветку на
   предыдущую группу; клиенты получат её при следующем запуске.
3. **Откат на конкретную старую группу**: `--group <groupId>` (id берутся из `ota:status`).
4. **Крайний случай** (переиздавать нечего): `git checkout` рабочей версии
   (каждый релиз тегируется `ota/v*` / `backup/*`) и повторная публикация.

Временно остановить раздачу канала: `npx eas channel:pause production`.

## 6. Нативная сборка (когда вердикт `NATIVE_BUILD`)

```bash
npm run build:eas:android    # черновик: eas build --platform android --profile production --no-wait
```

Никогда не публикуется автоматически. Особенности этого проекта для EAS Build:

- `android/xraylibs/libXray.aar` отсутствует в репозитории — на билд-сервере его
  скачивает хук `scripts/eas/download-libxray.sh` (npm-скрипт `eas-build-pre-install`,
  проверено на реальной сборке: AAR скачивается и распечатывается).
- **`EAS_NO_VCS=1` задаёт обёртка `scripts/eas/build-android.mjs`**: на этой машине
  внутренний `git clone file:///C:/...` у eas-cli падает (особенность среды), поэтому
  проект отправляется архивом. Облачный сервер всё равно использует коммит/версии с
  сервера (автоинкремент versionCode работает).
- `package-lock.json` обязан быть синхронен с `package.json` — сервер выполняет
  строгий `npm ci` (вложенный `typescript@5.9.3` от зависимостей `eas-cli` должен
  присутствовать в локе; ломал сборку, починено).
- Подпись: ключ загружен на EAS (конфигурация `default`, отпечаток совпадает с
  локальным `credentials/ghostcloud-release.keystore`). EAS сам подставляет его в
  Gradle через генерируемый `eas-build.gradle`; локальный `keystore.properties`
  для облака не нужен.
- Версиями управляет сервер (`cli.appVersionSource: remote`, `autoIncrement: true`).
  Стартовый versionCode задан 10 (выше локальных 5001–5004 с учётом схемы `*1000+abi`).

## 7. Авторизация

- Интерактивно: `npx eas login` (сессия в `~/.expo`).
- Автоматизация: переменная окружения `EXPO_TOKEN` (робот-аккаунт на
  <https://expo.dev/settings/access-tokens>), **никогда не хранится в коде/репозитории**.
- Проверка: `npx eas whoami`.

## 8. Регламент для агента (будущие задачи)

Для любого изменения (экран, дизайн, функция, фикс):

1. Сделать изменение и коммит в `release`.
2. `npm run ota:analyze` → вердикт.
3. **Если `OTA`**: `npm run ota:preview`, проверить на эмуляторе/тестовом устройстве
   с каналом `preview`, затем по явному подтверждению владельца — продакшен
   (двойной гейт).
4. **Если `NATIVE_BUILD`**: подготовить `npm run build:eas:android` (черновик) и
   сообщить владельцу; публикация — только вручную.
5. **Если `REVIEW_REQUIRED`**: остановиться и показать причины владельцу.
6. После каждого успешного релиза: тег `ota/v<версия>` (точка отката) и пуш.

Правило: **сомнение → `REVIEW_REQUIRED`**; ИИ-анализ не имеет права понижать вердикт.
